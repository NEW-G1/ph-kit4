검증 쿼리 10개를 `docs/requirements/us_covid_daily_checks/` 아래에 모두 썼습니다. 파일은 아직 실행하지 않았고 dry-run도 돌리지 않았습니다. 문법과 헤더는 L0·L1이 처음 확인합니다.

| 단계 | 파일 | 위반으로 돌려주는 행 |
|---|---|---|
| l3 | `C-01.sql` | raw 당일 파티션 행 수가 0이면 1행 |
| l3 | `C-02.sql` | stg의 키 중복, NULL, 음수 |
| l3 | `C-03.sql` | mart의 `report_date` 중복, NULL, 음수 |
| l4 | `C-04.sql` | raw 또는 stg 행 수가 원천 행 수와 다른 층 |
| l4 | `C-05.sql` | mart 행 수가 원천의 고유 date 수와 다른 경우 |
| l4 | `C-06.sql` | 날짜별 누적 확진·사망이 원천 합계와 다르거나 한쪽에만 있는 날짜 |
| l4 | `I-01.sql` | 신규 합계가 마지막 날 누적과 다른 경우 |
| l4 | `I-02.sql` | 신규가 누적의 전일 대비 차이와 다른 날. 첫 날은 누적값과 비교 |
| l4 | `I-03.sql` | 최소~최대 날짜 사이에 빠진 날짜 |
| l5 | `I-04.sql` | 원천에서 다시 계산한 기대값과 다른 행, 키 중복 |

- **작성 근거:** 요구서와 contract의 `checks`, `sql_rules.md`, 사다리 스크립트 `l5_idem.py`(L5가 무엇을 비교하는지 확인용)만 봤습니다. builder의 SQL과 `.dev/progress.md`는 보지 않았습니다. 파티션 조건은 contract의 snapshot 모드에 맞춰 `snapshot_date = DATE('{{ ds }}')`로 썼습니다.
- **쓰지 않은 검사:** contract만으로 쓸 수 없어 빼먹은 검사는 없습니다.
- **`allow_empty_days`:** `C-01`은 contract `load.allow_empty_days`가 없어 기본값 false로 보고 썼습니다.

사람이 결재 때 볼 것은 세 가지입니다.

1. **`error_type` 선택:** 머리말에는 값을 하나만 쓸 수 있습니다. 그래서 `C-02`와 `C-03`은 NULL·음수 위반도 포함하지만 `duplicate_rows`로 적었습니다. `C-01`(행 없음)은 맞는 항목이 없어 `range_violation`으로 적었습니다. 반려 분류가 부정확할 수 있습니다.
2. **`task` 선택:** 두 층을 함께 보는 `C-04`는 `task`를 `stg_us_states`로 적었습니다. 위반 행의 `layer_table` 열이 raw와 stg를 구분합니다.
3. **L5 검사의 한계:** `I-04`는 2회 실행 전후 비교를 하지 않습니다. 그 비교는 사다리가 따로 하고, 이 쿼리는 비교 뒤에 마트가 원천 재계산값과 같은지만 봅니다.

사다리로 검증되지 않는 완료 조건은 두 가지입니다.

- 산출물 생성(정의서·단위테스트 결과서·흐름도)은 사다리 L0~L5 범위 밖입니다.
- L6 OM 등록은 결재 후 단계입니다.

이 작업에서 `dags/sql/dq/` 게이트와 다른 파일은 만들지 않았습니다.
