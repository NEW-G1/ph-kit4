# 파이프라인 설계 원칙과 명명 규칙

> 파이프라인의 레이어, 설계 원칙, DAG 공통 설정, 명명 규칙을 정한 문서입니다. builder와 verifier, 사람 리뷰어가 마트를 설계하거나 DAG task를 추가할 때 읽습니다.
> 1단계 정답지(이전 저장소(1단계), 태그 `baseline-v1`)의 `pipeline_design.md`에서 **규칙만** 옮겼습니다.
> 테이블과 컬럼 정의, SQL 본문, 검증 수치는 옮기지 않았습니다. AI가 정답을 베끼면 측정이 무의미해지기 때문입니다.
> SQL 작성 규칙은 [sql_rules.md](sql_rules.md)에 있습니다.

---

## 1. 원천 데이터의 전제

원천과 운영 데이터셋 이름, 리전의 현재 값은 `dags/harness_config.json`(`source`, `datasets`)에 있습니다.

**원칙: 원천 전제(갱신 방식, 시간 컬럼, 리전, 크기)는 인터뷰에서 원천을 조회해 확인하고 요구서 §2 "원천과 레이어"에 적습니다.** 설계는 그 전제를 따릅니다.

### 적재 방식

하네스가 지원하는 적재 방식은 두 가지입니다. 마트마다 contract의 `load` 칸으로 고릅니다. 지원 범위는 저장소 README §1에 있고, 키트에서는 README의 "지원 범위"에 있습니다. (결정 79)

| 방식 | 하는 일 | 쓰는 때 |
|---|---|---|
| `snapshot`(기본값) | 원천 전체를 매일 `snapshot_date` 파티션에 복사합니다 | 원천이 쿼리당 500 MB 이하일 때 |
| `incremental` | 원천의 날짜 파티션에서 그 데이터 날짜 조각만 읽어 데이터 날짜 파티션(`load.partition_column`)에 넣습니다. 일 단위 지표만 지원합니다 | 원천이 크고 날짜 파티션이 있을 때 |

둘 다 아니면(원천이 크고 날짜 파티션이 없으면) 이 하네스로는 짓지 않습니다. 인터뷰에서 멈춰 요청자에게 알립니다.

### 리전과 크기

- 리전: 운영, 개발 데이터셋을 원천과 같은 리전에 둡니다. BigQuery는 한 쿼리에서 리전이 다른 테이블을 읽고 쓸 수 없습니다.
- 크기: 한 쿼리가 읽는 양이 500 MB 이하여야 합니다. 사다리가 쿼리마다 이 상한을 겁니다.

### 현재 원천의 예

현재 원천은 thelook_ecommerce(Google 공개 합성 데이터, 리전 US)입니다. 이 원천은 매일 데이터를 **랜덤으로 새로 생성**한 뒤 전체를 덮어씁니다. 그래서 두 마트의 설계는 아래 두 전제를 따릅니다.

1. **날짜가 다르면 같은 id라도 다른 레코드**입니다. 날짜 간 레코드를 이어 붙이거나 상태 변화를 추적하지 않습니다.
2. **하루치 스냅샷 안에 수년치 이력이 들어 있습니다.** 일간 추이는 스냅샷 날짜가 아니라 데이터 안의 생성 시각(예: `created_at`)으로 계산합니다.

## 2. 레이어 구조

아래 그림과 표의 원천, 운영 데이터셋 이름(`thelook_*`)은 현재 설정 값(`dags/harness_config.json`의 `source`, `datasets`)입니다. 설계는 원천이 바뀌어도 같습니다.

```
bigquery-public-data.thelook_ecommerce
  │  당일 전체 복사 + snapshot_date 부여
  ▼
raw    원천을 가공 없이 일자별 보관 → 게이트
  │  당일 파티션만 읽어 정제·조인
  ▼
stg    정제, 조인, 파생 컬럼. 분석 단위(grain)를 맞춤 → 게이트
  │  집계
  ▼
mart   분석·리포트용 집계 → 게이트

게이트 = 레이어 게이트 (ASSERT 검사, 테이블을 만들지 않음). 적재 task가 있는 층마다 1개
```

| 레이어 | 운영 데이터셋 | 역할 | 파티션 만료 |
|---|---|---|---|
| raw | `thelook_raw` | 원천을 가공 없이 일자별 보관. 하위 레이어가 외부 프로젝트가 아닌 우리 테이블만 읽게 하고, OM 리니지의 시작점이 됨 | 7일 |
| stg | `thelook_stg` | 정제, 조인, 파생 컬럼. 분석 단위(grain) 정리 | 7일 |
| mart | `thelook_mart` | 분석, 리포트용 집계 | 90일 |
| (검증) | `ai_dev` | 결재 전 검증 사다리 전용. 세 레이어를 모두 이 데이터셋 하나에 만든다. OM 수집 대상이 아님 | 데이터셋 기본 테이블 만료 7일, 기본 파티션 만료 없음. 사람이 설정함. snapshot 테이블은 DDL의 자체 만료를 따름 (결정 79) |

- 결재 전에는 `ai_dev`에서만 실행합니다. 결재(머지) 후에는 운영 DAG만 운영 데이터셋(현재 설정 값 `thelook_*`, `dags/harness_config.json`의 `datasets`)에 씁니다.
- 같은 SQL 파일을 데이터셋 이름만 바꿔 렌더링합니다([sql_rules.md §2](sql_rules.md#2-데이터셋-이름-파라미터)).
- raw, stg는 날짜 간 비교 의미가 없으므로 재실행과 디버깅에 필요한 7일만 보관합니다.
- mart는 파티션마다 전체 이력을 다시 집계하므로 90일이면 충분합니다.

## 3. 설계 원칙

| 원칙 | 내용 | 이유 |
|---|---|---|
| 스냅샷 파티션 | 모든 테이블은 `snapshot_date`(= Airflow `{{ ds }}`) 일 단위 파티션 | 실행 단위 관리, 재실행, 비용 절감 |
| 당일 파티션만 읽기 | 아래 "당일 파티션만 읽기" 참고 | 아래 참고 |
| 멱등성 | 같은 날짜로 재실행해도 결과가 같아야 함. 당일 파티션 DELETE 후 INSERT | 실패 재실행, 수동 재처리 안전성 |
| task = SQL = 테이블 | task 1개가 SQL 파일 1개로 테이블 1개를 만듦 | OM에서 파이프라인 task와 테이블 리니지를 1:1로 대응 |
| 레이어별 데이터셋 분리 | raw / stg / mart를 데이터셋으로 분리 | OM에서 도메인, 태그, 권한을 레이어 단위로 관리 |
| 리니지 친화적 SQL | 전체 경로 테이블명. 임시 테이블, 변수, 동적 SQL 금지 | OM이 쿼리 텍스트를 파싱해서 리니지를 만들기 때문 ([sql_rules.md §4](sql_rules.md#4-리니지-친화-sql-규칙)) |
| 컬럼 설명 필수 | 모든 테이블, 컬럼에 description을 쓴다 | 설명이 OM, 납품 정의서, 인수인계 문서, AgentGo용 카드 파일로 그대로 흘러감 |
| 개인 식별 정보 제외 | stg 이후로 전달하지 않음. 목록은 [pii_columns.md](pii_columns.md) | 개인정보 최소화 |
| mart는 같은 레이어 안에서 해결 | mart는 raw를 직접 읽지 않음. 필요한 단위(예: 고객 1명 = 1행)가 없으면 stg를 먼저 만든다 | 레이어 경계와 리니지를 단순하게 유지 |
| 합산 불가 지표 표시 | `COUNT(DISTINCT ...)`처럼 행끼리 더하면 중복되는 지표는 컬럼 설명에 "다른 행과 합산하면 중복 집계됨"을 적는다 | 조회하는 사람의 실수 방지 |

### 당일 파티션만 읽기

| 적재 방식 | 읽는 범위 | 이유 |
|---|---|---|
| snapshot | stg, mart는 항상 `snapshot_date = DATE('{{ ds }}')`만 읽음 | 스냅샷마다 원천 전체가 들어 있으므로 다른 날짜와 섞으면 중복됨. 현재 원천은 매일 재생성되기도 함 (§1) |
| incremental | raw는 원천의 `DATE(date_column) = DATE('{{ ds }}')` 조각만, stg, mart는 `<partition_column> = DATE('{{ ds }}')`(그 데이터 날짜 파티션)만 읽음 (결정 79) | 그 날짜 조각만 읽어야 스캔량이 원천 크기와 무관해짐 ([sql_rules.md §1-2](sql_rules.md)) |

그래서 incremental은 일 단위 지표만 지원합니다. 기간 지표는 동결 뒤 과제입니다.

## 4. DAG 공통 설정

| 항목 | 값 | 이유 |
|---|---|---|
| `schedule` | `None` | PoC라 서버를 개발할 때만 켬. 스케줄(7단계)은 보류 |
| `catchup` | `False` | 과거 날짜 자동 backfill 방지. raw 파티션 만료(7일)와 충돌 방지 |
| `max_active_runs` | `1` | 같은 테이블에 동시 DELETE/INSERT 방지 |
| Operator | `BigQueryInsertJobOperator` | SQL 파일을 그대로 실행. 레이어 게이트도 같은 Operator로 실패시킴 |
| `location` | `"US"` 상수 | 이 Operator의 `location`은 템플릿 필드가 아니어서 Jinja를 쓰면 안 됨 |
| SQL 파일 불러오기 | `{% include %}` + `template_searchpath` | SQL을 파일로 분리. 이 저장소는 `/opt/airflow/dags/harness/` 아래로 배포되므로 경로를 그에 맞춘다 |
| 의존성 | 레이어별 테이블 목록과 의존성 dict를 루프로 연결 | 새 task 추가 시 목록과 dict만 수정 |
| 레이어 게이트 재시도 | `retries=0` | 검사 결과는 재시도로 바뀌지 않음 |
| 강제 실패 파라미터 | boolean `Param`(기본 false). 참이면 게이트의 강제 실패 검사가 실패 | 운영 SQL을 고치지 않고 실패 경로를 시험. 잘못된 타입은 실행 생성 단계에서 거절 |

Airflow 문법(파라미터, 매크로, include 경로)은 설치된 2.10.5 문서로 확인합니다.

## 5. 레이어 게이트 배치 (품질 검사)

| 항목 | 규칙 |
|---|---|
| 방식 | BigQuery `ASSERT`. 위반 시 task와 DAG 실행이 failed |
| 위치 | 적재 task가 있는 층마다 게이트 task 1개. 테이블을 만들지 않고 조회만 함 |
| 결과 저장 | 결과 테이블을 만들지 않음 (리니지에 영향 없음) |
| 넣지 않는 것 | 원천이 매일 만드는 특성(예: 미래 날짜, 특정 기간 쏠림)은 `ASSERT`에 넣지 않음. DAG를 멈추면 안 되므로 "알려진 데이터 특성"으로 문서화 |
| 실패 메시지 | 검사마다 번호(`[C-xx]`, 강제 실패는 `[DQ-FORCE]`)를 메시지에 넣어 로그에서 바로 찾게 함 |

- 검증 사다리의 L3(레이어 게이트)는 이 `ASSERT`를 `ai_dev`에서 실행해 판정합니다.
- 게이트는 운영에도 남는 검사입니다. L4, L5처럼 개발 중에만 쓰는 루프 검증과 구분합니다.

## 6. 명명 규칙

| 대상 | 규칙 | 예 |
|---|---|---|
| raw 테이블 | `raw_<원천 테이블명>` | `raw_<source>` |
| stg 테이블 | `stg_<1행 단위를 드러내는 이름>` | `stg_<entity>` |
| mart 테이블 | `mart_<주기>_<주제>` (주기 없는 집계는 `mart_<주제>`) | `mart_daily_<subject>` |
| task_id | 만드는 테이블명과 같게 | 테이블이 `stg_<entity>`이면 task도 `stg_<entity>` |
| SQL 파일 | `dags/sql/<레이어>/<테이블명>.sql` | `dags/sql/mart/mart_daily_<subject>.sql` |
| 검사 SQL | `dags/sql/dq/` | |
| DAG | `harness_daily` (1단계 `thelook_daily`와 구분) | |
| 파티션 컬럼 | `snapshot_date` (DATE) | |
| 날짜 컬럼 | `_date` 접미사, DATE 타입 | `<event>_date` |
| 개수 | `_cnt` 접미사 | `<thing>_cnt` |
| 비율 | `_rate` 접미사, 0~1 | `<thing>_rate` |
| 불리언 | `is_` 접두사 | `is_<condition>` |
| 유효 기준 지표 | `valid_` 접두사 (취소, 반품 등 제외 기준을 설명에 적음) | `valid_<thing>_cnt` |

- 이름은 영문 소문자와 밑줄만 씁니다.
- 지표의 정확한 정의(계산식, 제외 조건)는 마트별 contract `interview.metrics`(결재 1에서 확정)가 기준입니다. `docs/domain/`은 결재된 지표 모음(참고)입니다. (결정 54)
