# 위임 기준 (진행표 3-11)

> AI에게 어디까지 맡기는지 한 곳에 모은 문서입니다. 작업을 반복 루프에 맡길지, 사람에게 물을지 정할 때 읽습니다.
> 새 원칙은 없고, 이미 정한 것만 옮겼습니다. 기본 내용은 `docs/plan/03_harness_guide.md`(원본 저장소 문서, 키트에 없음) §7, 추가한 행은 `docs/plan/00_handoff.md`(원본 저장소 문서, 키트에 없음)의 결정 번호가 근거입니다.

## 1. 기준 3개

| 기준 | 질문 |
|---|---|
| ① 자동 판정 | 사람 없이 성공과 실패를 판정할 수 있나? (dry-run, ASSERT, 단위 테스트) |
| ② 되돌리기 | 실패해도 브랜치 폐기나 git revert로 끝나나? |
| ③ 비밀·외부 무관 | 토큰, .env, 외부 전송, 권한 변경과 무관한가? |

- 세 기준을 모두 충족하는 작업만 반복 루프에 맡긴다.
- 사람이 눈으로 하던 확인을 스크립트로 바꾸면 위임 수준이 올라간다.

## 3. 요청 종류별 사다리 쓰임 (결정 58)

- 사다리는 하나이고, 요청 종류에 따라 돌리는 범위만 다르다.
- ladder_result의 `request_kind`로 구분한다.
- 본 측정은 `new_build`만 센다. `change`, `backfill_check`의 ladder_result는 `.dev/maintenance/`에 따로 보관한다(폴더는 첫 기록 때 만들어짐).

| 요청 종류 | `request_kind` | 사다리 쓰임 | 위임 | 지금 구현 |
|---|---|---|---|---|
| 신규 구축 | `new_build` | L0~L5 | 루프 | 구현됨 |
| 코드 수정 (버그 수정, 컬럼 추가, 로직 변경) | `change` | 바뀐 task와 DAG 의존성상 하류 task까지 L1~L5(회귀 검사). L0는 실행마다 한 번. contract가 바뀌면 멈추고 contract v2로 L0부터 다시(결정 45) | 루프. contract 변경은 사람 결재 | `--task`, `--all`로 실행. 하류 자동 포함(`--with-downstream`)은 미구현(`run_ladder.py`에 자리만 있음) |
| 재적재, 백필 검증 | `backfill_check` | ai_dev에서 같은 날짜 범위로 L2~L5를 미리 돌려 본다. 범위는 최근 7일까지. 운영 재적재 실행은 사람이 한다 | 미리 돌려 보기는 루프, 운영 실행은 사람 | `--ds` 하루씩. 날짜 범위(`--ds-from/--ds-to`)는 미구현(`run_ladder.py`에 자리만 있음) |
| 조사, 원인 분석 (읽기 전용) | 해당 없음 | 사다리 대상이 아니다. 보고서만 남긴다 | AI 조사, 사람 판단 | 해당 없음 |

## 4. 애매할 때

세 기준 중 하나라도 판단이 서지 않으면 만들거나 실행하기 전에 멈추고 사람에게 묻는다. (CLAUDE.md §3, §7)

예:
- 고치려면 테이블 키를 바꿔야 할 것 같은데, contract 변경인지 SQL 수정인지 판단이 서지 않는다. 멈추고 묻는다.
- 실행하려는 명령이 운영 데이터셋에 쓰는지 읽기만 하는지 확실하지 않다. 멈추고 묻는다.
